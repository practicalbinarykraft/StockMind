# Изменения: Ожидание завершения оценки новостей перед генерацией сценариев

## Проблемы
1. При запуске конвейера генерации сценариев система могла сообщать об отсутствии подходящих новостей, хотя процесс оценки новостей ещё не завершился
2. После парсинга и оценки новых новостей система не могла их найти из-за неправильного offset в пагинации
3. Система запрашивала все новости из БД без учёта возраста, что приводило к избыточным запросам

### Проблема 1: Преждевременная проверка новостей
Это происходило потому, что:
- Парсинг RSS источников запускал фоновую оценку новостей через AI
- Конвейер ждал всего 5 секунд после парсинга
- Оценка могла занимать больше времени, особенно при большом количестве новостей
- В результате конвейер начинал создавать сценарии до того, как все новости были оценены

### Проблема 2: Потеря новостей после парсинга
После парсинга и успешной оценки новостей:
- Новости получали оценки выше порога (например, 78/100 и 85/100)
- Но система не находила их при повторном поиске
- Причина: offset пагинации продолжал расти (offset=300), вместо сброса на 0
- Свежеспарсенные новости были в начале списка (сортировка по `publishedAt DESC`)
- Система искала их не там, где они были

### Проблема 3: Неэффективные SQL запросы
При пагинации с фильтром по возрасту (например, maxAgeDays=2):
- Система запрашивала все новости из БД по 50 штук
- Фильтрация по дате происходила после получения из БД в JavaScript
- При большой базе (например, 1000+ новостей старше 2 дней) это приводило к:
  - Множеству ненужных SQL запросов
  - Передаче лишних данных через сеть
  - Напрасной нагрузке на память
- Пример: если все новости старше 2 дней, система проходила через всю БД, запрашивая порции по 50 новостей

## Решение

### Серверная часть

#### 1. `server/lib/rss-background-tasks.ts`
- Добавлена глобальная карта активных промисов оценки (`global.activeScoringPromises`)
- При запуске оценки промис сохраняется в карту по ID источника
- После завершения оценки промис автоматически удаляется из карты
- Добавлена функция `waitForAllScoring()` для ожидания завершения всех активных задач оценки с таймаутом (по умолчанию 2 минуты)

```typescript
// Пример использования
await waitForAllScoring(120000); // Ждём до 2 минут
```

#### 2. `server/modules/generation/generation-pipeline.ts`
- Добавлен импорт `gte` из drizzle-orm для операции "больше или равно"
- Метод `parseAllUserSources()` теперь ожидает завершения оценки новостей
- Удалена фиксированная задержка в 5 секунд (больше не нужна)
- **КРИТИЧЕСКОЕ ИСПРАВЛЕНИЕ #1**: После парсинга offset пагинации сбрасывается на 0
  - Это позволяет найти свежеспарсенные новости, которые находятся в начале списка
  - Без этого fix новости с оценками терялись из-за неправильного offset
- **ОПТИМИЗАЦИЯ #2**: Фильтр по дате перенесён на уровень SQL запроса
  - В оба цикла пагинации (до и после парсинга) добавлено условие `gte(rssItems.publishedAt, cutoffDate)`
  - База данных теперь отфильтровывает старые новости сразу, используя индекс
  - Это предотвращает ненужные запросы и передачу данных
  - JavaScript-фильтрация оставлена как дополнительная защита для поля `parsedAt`
- Добавлены SSE уведомления о начале и завершении оценки:
  - `scoring_started` - оценка новостей начата
  - `parsing_completed` - парсинг и оценка завершены

**Последовательность работы:**
1. Парсинг RSS источников (параллельно)
2. Ожидание завершения оценки всех новостей
3. **Сброс offset на 0** для повторного поиска
4. Повторный поиск подходящих новостей **с начала списка**
5. **SQL запросы теперь фильтруют по дате сразу** - не запрашивают старые новости
6. Генерация сценариев

### Клиентская часть

#### `client/src/features/conveyor/components/ConveyorDashboard.tsx`
- Добавлена обработка новых SSE событий:
  - `parsing_started` - показывает toast с информацией о начале парсинга
  - `scoring_started` - показывает toast о начале оценки новостей
  - `parsing_completed` - показывает toast о завершении парсинга и оценки
  - `parsing_error` - показывает ошибку парсинга

## Технические детали

### Преимущества решения:
1. ✅ Гарантированное завершение оценки перед генерацией
2. ✅ Таймаут защищает от бесконечного ожидания
3. ✅ Пользователь видит прогресс через SSE уведомления
4. ✅ Не блокирует другие операции (асинхронное выполение)
5. ✅ Автоматическая очистка завершённых промисов
6. ✅ **Правильный сброс offset** гарантирует нахождение новых новостей
7. ✅ **SQL-фильтрация по дате** - значительное улучшение производительности

### Пример проблемы #2 до исправления:
```
Оценка новостей:
- "Новость 1": 78/100 ✅ (выше порога 75)
- "Новость 2": 85/100 ✅ (выше порога 75)

Повторный поиск:
- offset=300 (продолжение с того же места)
- Новости в начале списка (publishedAt DESC)
- Результат: 0 новостей найдено ❌

После исправления:
- offset=0 (начинаем сначала)
- Новости в начале списка
- Результат: 2 новости найдено ✅
```

### Пример проблемы #3 до исправления:
```
Настройки: maxAgeDays = 2 (нужны новости не старше 2 дней)
База данных: 1000 новостей, все старше 5 дней

До оптимизации:
┌─────────────────────────────────────────────────┐
│ SQL: SELECT * FROM rss_items LIMIT 50 OFFSET 0 │
│ Результат: 50 старых новостей                   │
│ JS фильтрация: 0 подходящих                     │
├─────────────────────────────────────────────────┤
│ SQL: SELECT * FROM rss_items LIMIT 50 OFFSET 50│
│ Результат: 50 старых новостей                   │
│ JS фильтрация: 0 подходящих                     │
├─────────────────────────────────────────────────┤
│ ... ещё 18 запросов ...                         │
├─────────────────────────────────────────────────┤
│ Итого: 20 SQL запросов, 1000 новостей передано │
│ Результат: 0 новостей найдено                   │
└─────────────────────────────────────────────────┘

После оптимизации:
┌─────────────────────────────────────────────────────────────────┐
│ SQL: SELECT * FROM rss_items                                    │
│      WHERE publishedAt >= '2026-02-01' LIMIT 50 OFFSET 0        │

Экономия: 19 SQL запросов и 1000 записей не передано!
```

### Таймауты:
- Ожидание оценки: 120 секунд (2 минуты)
- При превышении таймаута система продолжает работу с предупреждением в логах

### Логирование:
```
[RSS] Waiting for 3 scoring tasks to complete (timeout: 120000ms)
[RSS] All scoring tasks completed successfully
[Pipeline] Оценка новостей завершена
```

## Проверка работы

1. Запустите конвейер генерации без подходящих новостей
2. Система автоматически запустит парсинг источников
3. Увидите уведомление "Парсинг источников"
4. Увидите уведомление "Оценка новостей"
5. Увидите уведомление "Парсинг завершён"
6. Только после этого начнётся генерация сценариев

- Существующие процессы генерации не будут затронуты
- Таймаут можно настроить при вызове `waitForAllScoring(customTimeout)`
